## 0. TL;DR — the verdict, up front

1. **Use `ex_cldr`, not Localize 1.0.** This inverts the obvious choice, and the reason is
   structural, not stylistic: Localize is a *runtime-data* library
   (`Application.app_dir(:localize, "priv/localize/…")` + `Application.get_env/2` +
   its own OTP supervisor). Mob deploys dependency BEAMs into a **flat directory with no
   `-vsn/ebin` structure and no dependency `priv/`**, does not start dependency OTP
   applications, and does not ship `config/config.exs` to the device. All three of Localize's
   load-bearing assumptions are false on Mob. `ex_cldr` bakes 100 % of its CLDR data into
   compile-time module attributes and needs none of them. See §1.4 and §5.3 — this is the
   single most important finding in this document.
2. **Persian calendar: `ex_cldr_calendars_persian` is the correct *algorithm*, but must not
   be called at runtime.** It is observational/astronomical (`Astro.equinox` + `Astro.solar_noon`
   at the Tehran meridian, per date, uncached). Measured **476 µs per
   Gregorian→Persian conversion** on an M-series Mac. Precompute the Nowruz table at build
   time; I verified a 101-integer table reproduces it with **0 mismatches over 1826
   consecutive days** at **1.26 µs/op — ~380× faster**. See §2.
3. **Persian digits, separators, month/weekday names, week-starts-Saturday and RTL-ness are
   all free from CLDR** — no hand-written tables. Verified outputs in §3.
4. **Mob has zero RTL support on either platform, and zero locale plumbing.** No
   `layoutDirection`, no `LocalLayoutDirection`, no `rtl`, no locale NIF anywhere in mob
   0.7.20, in the generated Compose bridge, or in the generated `AndroidManifest.xml`
   (`android:supportsRtl` is absent, and Android's default is `false`). **This is a
   native-code work item, not a configuration flag.** See §4 — shout about this one.
5. **On-device cost is small once beams are stripped**: the whole en+fa CLDR stack measured
   **29.24 MB unstripped → 2.61 MB stripped → 2.49 MB gzipped**. Mob's Android release path
   does run `beam_lib:strip_release/1`. See §5.

### 1.2 What Localize 1.0 actually gives over gettext/ex_cldr

Source: <https://forum.elixirforum.com/t/localize-reaches-1-0/76203>,
<https://github.com/elixir-localize/localize>, <https://localize.hexdocs.pm/readme.html>,
and the shipped `usage-rules.md` inside `localize-1.2.0.tar`.

Real, substantive improvements:

- **No compile-time backend modules.** From `localize-1.2.0/usage-rules.md`:
  > "There is no compile-time backend module. Do not write `use Localize` or
  > `defmodule MyApp.Localize`. All 766 CLDR locales are available immediately."
- **Compile speed.** The forum announcement claims "under 3 seconds on M1 MacBook Pro …
  an order of magnitude faster" than ex_cldr. My measurement of the ex_cldr side is
  consistent with that being a real problem: a cold `mix compile` of ex_cldr +
  numbers + dates_times + calendars + persian + messages for **two** locales took
  **4 m 36 s** (`264.78s user 31.72s system 107% cpu 4:35.89 total`).
- **Runtime locale loading** into `:persistent_term`, with pluggable providers
  (`Localize.Locale.Provider.PersistentTerm`) and optional CDN download.
- **Consolidation**: one dep replaces the whole `ex_cldr_*` family
  (numbers, dates/times, units, lists, collation, MessageFormat 2, currencies).
- **Structured errors**: `{:error, Exception.t()}` instead of `{:error, {module, message}}`.
- **`Localize.Gettext.Interpolation`** — a `Gettext.Interpolation` behaviour implementation
  that lets you put **MessageFormat 2** directly in `.po` files
  (`localize-1.2.0/lib/localize/gettext/interpolation.ex:1-40`). This is genuinely nice:
  plural selection and number formatting happen inside the translation, not around it.
- **`calendrical` 1.2.1** folds ~25 calendars (incl. Persian) into one package instead of
  one hex package per calendar.
- **ICU4C NIF backend** (`backend: :nif`) for number/date/collation formatting, with pure-Elixir
  fallback.
- `ex_cldr` is in maintenance: the forum thread states it "receives maintenance until end of
  2027 but no new features".

### 1.3 What `ash_localize` adds — and its status

Source: <https://github.com/team-alembic/ash_localize>, README fetched raw
(`https://raw.githubusercontent.com/team-alembic/ash_localize/main/README.md`),
plus the GitHub API.

Repo facts: created **2026-05-21**, last push **2026-08-02**, **4 stars**, **no tags, no
releases, not on Hex.pm** (hex.pm/api/packages/ash_localize → `404 Page not found`).

Its own README, verbatim:

> **Status: early development.** The types, formatting, error messages and locale
> resolution described below are implemented and tested. The AshPostgres,
> AshPhoenix, AshGraphql and AshJsonApi integrations, and the translated-content
> DSL, are not yet built — see `docs/PLAN.md`.

What it **does** give:

- Validated Ash types that canonicalise through Localize: `:locale`, `:territory`,
  `:currency_code`, `:timezone` (`"en-us"` → `"en-US"`).
- Semantic number types — `:count`, `:ordinal`, `:percentage`, `:ratio`, `:score`, `:rating`
  — carrying the metadata needed for pluralisation.
- ~15 `Format*` calculations that read the locale from **Ash context**, not the process
  dictionary. That is the real Ash-specific value, and the README explains why:
  > "Localize keeps it in the process dictionary, which does not survive the processes Ash
  > spawns for parallel loads and async calculations — so a value formatted inside one
  > silently comes back in the default locale."
- A resolution chain: explicit `:locale` argument → Ash context `:locale` → actor-derived
  (opt-in) → application default.
- `AshLocalize.translate_error/2` for localised Ash error messages via MF2.

What it **does not** give:

- **Translated attributes / translated content. Not built.** The README lists
  `localize_translate` for translated content under "Planned, and not yet built".
- No `ash_postgres`/`ash_phoenix`/`ash_graphql`/`ash_json_api` integration yet.
- No gettext dependency; error translation uses its own catalogue, not `.po`.

**Verdict: not production-ready, and not needed by Kati.** Kati is device-first with no
server, no GraphQL/JSON:API, no Postgres, and — per the design's own content boundary
(design-index.md:394-396) — *no translated user content at all*:

> "Your own words — notes, list names, meal titles — are never translated. Only the
> interface changes."

The one thing ash_localize solves well (locale surviving Ash's parallel-load processes) is
solvable in Kati with three lines: pass `locale:` explicitly at the formatting call site,
which you have to do anyway on Mob (see §6.4). Skip it.

### 1.4 Why Localize 1.0 does not work on Mob (the decisive finding)

Three independent blockers, each verified.

**(a) `Application.app_dir/2` raises under Mob's code-path layout.**

Mob copies every dependency's compiled beams into a single flat directory:

```elixir
# mob_dev/lib/mob_dev/native_build.ex:1678-1687
defp copy_app_beams(otp_root, app_module) do
  beams_dir = Path.join(otp_root, app_module)
  ...
  Path.wildcard("_build/dev/lib/*/ebin/*")
  |> Enum.each(fn src ->
    File.cp!(src, Path.join(beams_dir, Path.basename(src)))
  end)
```

There is no `<app>-<vsn>/ebin` directory for any dependency, and **no dependency `priv/` is
copied at all** — only the *host app's* `priv/`
(`native_build.ex:2220-2240`, `copy_priv_repo_assets/2`, an `rsync -a priv/ …`), and only the
*host app* gets a real OTP lib dir (`native_build.ex:3400-3436`, `install_app_in_otp_lib/2`,
whose comment reads *"required for code:priv_dir"*).

Mob's own generated `app.ex` states the consequence verbatim
(`fresh_mob_beam/lib/fresh_mob_beam/app.ex:47-52`):

> "On Android and iOS, Mob deploys .beam files to a flat -pa directory with no
> versioned lib structure, so `:code.priv_dir/1` returns `{error, bad_name}`."

I reproduced it exactly (Erlang/OTP 28 [erts-16.1.1], Elixir 1.19.5) with a flat directory
containing only `fakeapp.app` on the code path:

```
code:lib_dir(:fakeapp): {:error, :bad_name}
where_is_file:          ~c".../mobsim/kati/fakeapp.app"
RAISED: %ArgumentError{message: "unknown application: :fakeapp"}
```

Localize reads its data from exactly that path at **runtime**:

```elixir
# localize-1.2.0/lib/localize/supplemental_data.ex:6-20
defp localize_dir do
  Application.app_dir(:localize, "priv/localize")
end

defp load_supplemental(filename) do
  key = {:localize, :supplemental, filename}
  Localize.DataLoader.load(key, fn ->
    localize_dir() |> Path.join("supplemental_data") |> Path.join(filename)
    |> File.read!() |> :erlang.binary_to_term()
  end)
end
```

`likely_subtags`, `aliases`, `plural_rules_cardinal`, `territories`, `collation_tailoring`,
validity tables and `Localize.version/0` (`lib/localize.ex:181-190`) all go through this.
On device it raises `ArgumentError` before it ever gets to `File.read!`.

By contrast, **every** ex_cldr priv read is a compile-time module attribute:

| ex_cldr read | site | when |
|---|---|---|
| `@cldr_data_dir Path.join(Application.app_dir(@app_name), "priv/cldr")` | `lib/cldr/config/config.ex:58` | compile |
| `@all_language_tags Cldr.Config.all_language_tags()` | `lib/cldr/locale.ex:285` | compile |
| `@language_matching Cldr.Config.language_matching()` | `lib/cldr/locale/match.ex:29` | compile |
| `@distance_trie Cldr.Locale.DistanceTrie.Builder.build()` | `lib/cldr/locale/distance_trie.ex:213` | compile |
| `@validity_data Cldr.Config.validity(:t)` | `lib/cldr/validity/t.ex:20` | compile |
| `@rules Cldr.Config.cldr_data_dir() …` | `lib/cldr/plural_rules/plural_rule.ex:116` | compile |
| `@data_dir [:code.priv_dir(@app_name), "/cldr/locales"]` | `ex_cldr_units/lib/cldr/unit.ex:145` | compile |

`ex_cldr_numbers`, `ex_cldr_dates_times`, `ex_cldr_calendars` and
`ex_cldr_calendars_persian` contain **no** `Application.app_dir` / `:code.priv_dir` call at all
(verified by grep across their `lib/` trees). The only runtime `:code.priv_dir` in the family
is `ex_cldr_messages/lib/cldr/messages/v2/nif.ex:15`, and that NIF is explicitly optional:

> "The NIF is optional — when unavailable, `available?/0` returns `false` and calls raise
> `:nif_library_not_loaded`."

**(b) Mob starts no dependency OTP applications.**

The generated BEAM entry (`fresh_mob_beam/src/fresh_mob_beam.erl`) is the whole boot:

```erlang
start() ->
    step(1, fun() -> application:start(compiler) end),
    step(2, fun() -> application:start(elixir)   end),
    step(3, fun() -> application:start(logger)   end),
    step(4, fun() -> mob_nif:platform()          end),
    step(5, fun() -> 'Elixir.FreshMobBeam.App':start() end),
    timer:sleep(infinity).
```

Localize needs `Localize.Supervisor` running (data loader, locale loader + its validation
ETS table, cache sweeper, format cache, collation table —
`localize-1.2.0/lib/localize/supervisor.ex:1-20`). That is *fixable* (call
`Localize.Supervisor.start_link([])` in `on_start/0`; Localize documents that path), but it
is one more thing to remember. ex_cldr needs no supervisor for formatting.

**(c) `config/config.exs` does not reach the device.**

The compiled `.app` file for a Mob project has **no `{env, …}` key at all**:

```
{application,fresh_mob_beam,[{modules,[…]},{optional_applications,[]},
 {applications,[kernel,stdlib,elixir,logger,mob,ecto_sqlite3,…]},
 {description,"fresh_mob_beam"},{registered,[]},{vsn,"0.1.0"}]}.
```

and `mob_dev` never generates a `sys.config`, never runs `Mix.Tasks.Loadconfig` on device,
and never calls `Config.Reader` for *application* config at deploy time (its `Config.Reader`
uses are all for reading `mob.exs` on the build host). So `config :localize, otp_app: :kati,
default_locale: :fa, supported_locales: [:en, :fa]` — the entire documented Localize setup —
is a **no-op on device**. Localize reads all of it through `Application.get_env/2` at runtime
(`lib/localize.ex:481`, `:916`; `lib/localize/locale/provider.ex:182`, `:187`, `:319`;
`lib/localize/locale.ex:377`; `lib/localize/format_cache.ex:114`; …).

Compounding it, ash_localize's own README warns about the silent-failure mode this produces:

> "Localize ships `:en` and fetches every other locale from its CDN. **A locale it
> cannot find falls back to `:und` and still returns `{:ok, ...}`** — the output is
> wrong for the requested locale and nothing in the return value says so."

On Mob that is exactly what you would ship: a Persian UI silently rendering root-locale data,
with `{:ok, _}` everywhere. Unacceptable.

*(NOT VERIFIED ON A DEVICE — the `.app`-has-no-env and no-sys.config findings are from static
inspection of the build pipeline. Before relying on this either way, run a one-line probe on
device: `IO.inspect(Application.get_env(:mob, :repo))`. If it returns `nil`, config.exs is
confirmed absent and every dependency must be configured with `Application.put_env/3` inside
`on_start/0`.)*

Also worth knowing: Localize's CDN host `https://elixir-localize.com/locales/v1.2.0/fa.etf`
returned **HTTP 404** when I tried it (the root `https://elixir-localize.com/` is 200). So the
runtime-download path is not even reachable for `fa` right now. Local `priv/localize/locales/`
in the tarball contains **only `en.etf` (615.9 KB) and `und.etf` (336.1 KB)**.

### 1.5 What ex_cldr costs you in exchange

Be honest about the trade:

- **Compile time**: 4 m 36 s cold for two locales. Incremental rebuilds of `Kati.Cldr` alone
  still print *"Compiling lib/kati/cldr.ex (it's taking more than 10s)"*.
- **Compile-time network access**: `ex_cldr` ships only `en`, `en-001`, `und` in
  `priv/cldr/locales` and downloads the rest from GitHub during compilation
  (`lib/cldr/install.ex:5-14`: *"When installed as a package on from hex, Cldr has only the
  default locales `["en", "und"]` installed and configured. When other locales are added to
  the configuration Cldr will attempt to download the locale from github during
  compilation."*). My build logged `Downloaded locale :fa version v2.47.5`. CI needs network,
  or commit `cldr_data/locales/fa.json` (607 KB — verified, `fa.json` is 620,929 bytes).
- Maintenance-only status until end of 2027.

None of these are runtime problems, and all of Localize's advantages are *runtime* advantages.
For a device-first app with two fixed locales, ex_cldr's compile-time-everything model is
precisely the right shape.

## 2. Jalali / Shamsi

### 2.1 Which library

| candidate | verdict |
|---|---|
| `jalaali` 0.4.1 | **No.** Last release 2023-06-25. Standalone conversion + a bare `Calendar` implementation with **no CLDR integration** — no Persian month names, no locale-aware formats, no `Cldr.Calendar` behaviour. You would hand-write every string the design already gets free from CLDR. |
| Ash's own | **Does not exist.** Ash has no calendar system; `ash_localize` explicitly defers calendars to Localize/`calendrical`. |
| `calendrical` 1.2.1 (`Calendrical.Persian`) | Correct algorithm, part of the Localize family — but see §1.4: the Localize family cannot run on Mob today. Also still depends on `{:astro, "~> 2.5"}` and `Geo`. |
| **`ex_cldr_calendars_persian` 1.1.1** | **Yes — as the build-time source of truth.** Conforms to both `Calendar` and `Cldr.Calendar`, sets `cldr_calendar_type: :persian` so all CLDR `persian` name data resolves, and `Cldr.Calendar.Preference.calendar_from_locale(:fa)` auto-selects it. |

Verified end-to-end in the throwaway project:

```
gregorian 2026-08-16 -> persian: ~D[1405-05-25 Cldr.Calendar.Persian]
calendar from locale fa: {:ok, Cldr.Calendar.Persian}
```

`~D[1405-05-25]` is exactly the design's *"یکشنبه ۲۵ مرداد ۱۴۰۵"* (design-index.md:380).

### 2.2 Storage: Gregorian/UTC in, Shamsi out — the actual rule

**Shamsi is a `Date` view, never a stored value.** The mechanism is Elixir's own
`Calendar` behaviour: a `%Date{}` carries a `:calendar` field, and `Date.convert/2` changes
only that field plus the y/m/d numbers — the underlying ISO-day count is invariant.

- **Store** `DateTime` in UTC (`Calendar.ISO`) and `Date` in `Calendar.ISO`. Ash/Ecto's
  `:utc_datetime_usec` / `:date` types are ISO-only; SQLite stores an ISO-8601 string.
  Nothing changes in the data layer, no custom Ecto type, no migration.
- **Render**: `Date.convert!(date, Kati.Calendar.Shamsi)` at the last possible moment, then
  `Kati.Cldr.Date.to_string/2`.
- **Read back a user-picked Shamsi date** (§2.6).

Do **not** define an Ash attribute whose calendar is Persian. `Date.compare/2` across
calendars works but `Date.range/2`, SQL comparisons, and every third-party integration
(Google Calendar sync, iCal export) assume ISO. Keep exactly one representation in the
database.

### 2.3 Leap years and the 33-year cycle

`ex_cldr_calendars_persian` does **not** use the 33-year arithmetic approximation, and it does
not use Birashk's 2820-year cycle either. It is **observational**:

```elixir
# ex_cldr_calendars_persian-1.1.1/lib/cldr/calendar/persian.ex:32-38, 96-104
@spec leap_year?(Calendar.year) :: boolean()
def leap_year?(year) do
  new_year  = date_to_iso_days(year, 1, 1)
  next_year = date_to_iso_days(year + 1, 1, 1)
  next_year - new_year == 366
end

@tehran %Geo.PointZ{coordinates: {51.3890, 35.6892, 1100}}
defp midday_in_tehran(date), do: Astro.solar_noon(@tehran, date)
defp vernal_equinox(year),   do: Astro.equinox(year, :march)
```

This is the *legally correct* definition — the Iranian calendar's year begins on the day of
the March equinox as observed at the Iran Standard Time meridian, not on an arithmetic rule.
The 33-year cycle is an emergent *description*, not the definition, and arithmetic
approximations disagree with the true calendar in some years.

Measured leap years, 1390–1440 SH:

```
[1391, 1395, 1399, 1403, 1408, 1412, 1416, 1420, 1424, 1428, 1432, 1436]
```

Gaps: 4, 4, 4, **5**, 4, 4, 4, 4, 4, 4, 4. The single 5-year gap (1403 → 1408) *is* the
33-year cycle showing itself, and it matches published Iranian calendar tables. Any
implementation that produces a uniform 4-year gap there is wrong.

`calendrical` 1.2.1 has the identical algorithm plus an explicit range guard:

> "This calendar is observational: each year begins at the vernal equinox observed in Tehran,
> computed by `Astro.equinox/2`, which is accurate only for Gregorian years 1000 to 3000."

### 2.4 The performance problem — and the fix (do not skip this)

`new_year_on_or_before/1` calls `new_year_gregorian/1` **twice** per invocation, and each of
those runs a full `Astro.equinox` + `Astro.solar_noon` floating-point computation. Nothing is
cached. Measured on an Apple-silicon Mac (`MIX_ENV=prod`, warm):

| operation | µs/op |
|---|---|
| `Date.convert!(gregorian, Cldr.Calendar.Persian)` | **476.5** |
| `Cldr.Calendar.Persian.date_to_iso_days/3` | 95.3 |
| `Cldr.Calendar.Persian.leap_year?/1` | 170.3 |
| format a **Persian** date, `fa`, `"EEEE d MMMM y"` | **317.5** |
| format a **Gregorian** date, `fa`, `"EEEE d MMMM y"` | 66.2 |
| format a Gregorian date, `en`, `:long` | 29.0 |

A 42-cell month grid is ~7.9 ms of pure calendar conversion **on a Mac**. A mid-range Android
phone running the same Elixir will be several times slower, and it is per render, not per
mount. That is a visible hitch on screens 02/56/60.

**Fix, verified:** precompute Nowruz as an ISO-day integer per Gregorian year and do the rest
in integer arithmetic.

```
mismatches over 1826 days (2024-01-01 .. 2028-12-31): 0
table-driven conversion: 1.26 us/op
table size (2000..2100): 101 integers
```

**Zero** mismatches against `ex_cldr_calendars_persian` over five consecutive years, at
**~380× the speed**. Nowruz dates the table produced, spot-checked: 2024-03-20, 2025-03-21,
2026-03-21, 2027-03-21, 2028-03-20, 2029-03-20, 2030-03-21 — correct.

The conversion, once you have the table:

```elixir
iso  = Date.to_gregorian_days(date)
gy   = date.year
ny   = if table[gy] <= iso, do: table[gy], else: table[gy - 1]
year = if table[gy] <= iso, do: gy - 621, else: gy - 622
doy  = iso - ny + 1
{month, day} =
  if doy <= 186,
    do:   {div(doy - 1, 31) + 1,     rem(doy - 1, 31) + 1},
    else: {div(doy - 187, 30) + 7,   rem(doy - 187, 30) + 1}
```

(First six months are 31 days, next five 30, Esfand 29 or 30 — the design's own summary of
the Solar Hijri month lengths.)

So: **keep `ex_cldr_calendars_persian` as a `only: :dev` dependency used by a one-off mix
task that emits the table**, and ship `Kati.Calendar.Shamsi` built on
`use Cldr.Calendar.Behaviour, epoch: ~D[0622-03-20 Cldr.Calendar.Julian], cldr_calendar_type: :persian`
with the table baked in as a module attribute. That also drops `astro` (0.19 MB ebin) and
`geo` (0.35 MB ebin) from the shipped bundle and removes all float math from the render path.

### 2.5 Month grids that must start on شنبه, and week numbering

**Week start comes from CLDR territory data and is already correct.** From
`ex_cldr-2.47.5/priv/cldr/weeks.json`:

```
first_day      IR = 6      (Saturday; 1 = Monday … 7 = Sunday)
weekend_start  IR = 5      (Friday)
weekend_end    IR = 5
first_day     001 = 1      min_days 001 = 1
first_day      US = 7      min_days US  = 1
first_day      GB = 1      min_days GB  = 4
```

Verified at runtime:

```
first day fa: 6
first day en: 7
```

⚠️ **`first_day_for_locale(:en)` is 7 (Sunday), not Monday.** The design's locale table
(design-index.md:166) says English → Monday. `:en` resolves to territory `US`. If you want
Monday, use `:"en-GB"` as the locale, or pass `day_of_week: 1` explicitly. Decide this
deliberately — it is a one-character difference that changes every calendar screen.

⚠️ **`Cldr.Calendar.Persian` does not implement weeks at all.** Verified:

```
Cldr.Calendar.Interval.week(persian_date): {:error, :not_defined}
Cldr.Calendar.week_of_year(persian_date):  {:error, :not_defined}
Cldr.Calendar.week_of_month(persian_date): {:error, :not_defined}
```

This is a behaviour default, not a bug in the Persian module —
`ex_cldr_calendars-2.4.4/lib/cldr/calendar/behaviour.ex` and
`calendrical-1.2.1/lib/calendrical/behaviour.ex:397-423` both default `week_of_year/3` and
`iso_week_of_year/3` to `{:error, :not_defined}` and Persian never overrides them. **Both
library families have this gap.** A knock-on: `Cldr.Calendar.localize(date, :days_of_week, …)`
crashes for Persian dates, because its implementation iterates `Interval.week(datetime)`
(`ex_cldr_calendars-2.4.4/lib/cldr/calendar.ex:2833-2847`).

So screens 56 (day strip starting شنبه) and 60 ("the hardest case in the whole pass: a matrix
whose columns are days") need Kati's own week logic. It is four lines:

```elixir
# leading blank cells in a month grid, for any week-start
@spec lead_blanks(Date.t(), 1..7) :: 0..6
def lead_blanks(first_of_month, first_day_of_week) do
  rem(Cldr.Calendar.iso_day_of_week(first_of_month) - first_day_of_week + 7, 7)
end

# weekday header row, already in display order
def weekday_order(6), do: [6, 7, 1, 2, 3, 4, 5]   # Saturday-first (fa)
def weekday_order(1), do: [1, 2, 3, 4, 5, 6, 7]   # Monday-first  (en-GB)
def weekday_order(7), do: [7, 1, 2, 3, 4, 5, 6]   # Sunday-first  (en-US)
```

Sanity check against the real data: 1 Mordad 1405 has `iso_day_of_week = 4` (Thursday);
`lead_blanks(_, 6) = rem(4 - 6 + 7, 7) = 5` — Sat, Sun, Mon, Tue, Wed blank, then Thursday.
Correct. `Cldr.Calendar.days_in_month/1` **does** work for Persian (`31` for Mordad 1405), as
does `Cldr.Calendar.Interval.month/1` (31 dates).

This directly answers the design's own note that *"Mirroring alone would put Monday on the
right and still be wrong — the sequence itself has to restart at شنبه"*: the sequence is
data (`weekday_order/1`), not layout. RTL mirroring (§4) and week ordering are two separate
mechanisms and must stay separate.

**Weekday labels are free.** From the CLDR `fa` data, `dates.calendars.persian.days`:

```
format.wide       1..7 = دوشنبه، سه‌شنبه، چهارشنبه، پنجشنبه، جمعه، شنبه، یکشنبه
format.short      1..7 = ۲ش، ۳ش، ۴ش، ۵ش، ج، ش، ۱ش
stand_alone.narrow 1..7 = د، س، چ، پ، ج، ش، ی
```

Reorder `stand_alone.narrow` by `weekday_order(6)` → **ش ی د س چ پ ج** — character-for-character
the design's abbreviations (design-index.md:381-382). Nothing hand-written.

**Month names are free too**: فروردین اردیبهشت خرداد تیر مرداد شهریور مهر آبان آذر دی بهمن اسفند.

### 2.6 Converting a user-picked Shamsi date back to UTC

Three steps, no ambiguity, and one trap.

```elixir
# 1. Build the Date in the Shamsi calendar from the picker's raw y/m/d.
{:ok, shamsi} = Date.new(1405, 5, 25, Kati.Calendar.Shamsi)

# 2. Convert to ISO. This is exact — same ISO-day count, different field values.
{:ok, iso_date} = Date.convert(shamsi, Calendar.ISO)     #=> ~D[2026-08-16]

# 3. Attach the wall-clock time the user chose IN THEIR ZONE, then shift to UTC.
{:ok, naive}    = NaiveDateTime.new(iso_date, ~T[07:30:00])
{:ok, local}    = DateTime.from_naive(naive, "Asia/Tehran")
utc             = DateTime.shift_zone!(local, "Etc/UTC")
```

The trap: **step 3 is where correctness lives, not step 2.** A calendar conversion is
timezone-free; a "date the user picked" is not. Iran abolished DST in 2022 so `Asia/Tehran`
is a stable UTC+03:30, but Kati must still run a real tzdata source
(`{:tz, "~> 0.28"}` or `{:tzdata, …}` + `config :elixir, :time_zone_database`) because the
app is device-first and the user may travel. Verify the tz database ships and resolves on
device — **NOT VERIFIED**; `Mob.Device` has no timezone API and I did not find a tz database
in the Mob dependency tree.

For an all-day event (a habit, a book finished on a date) store a plain `:date` in ISO and
never involve a timezone at all. For anything with a clock time (a meal at ۰۷:۳۰, an episode
airing) store `:utc_datetime_usec`. That split matters more than the calendar does.

### 3.2 ⚠️ The transliteration performance warning — fix it at compile time

Formatting anything in `fa` logs, on **every call**:

```
[warning] Transliteration from number system :latn to :arabext requires dynamic generation
of a transliteration map for each function call which is slow. Please consider configuring
this transliteration pair. See `Cldr.Number.Transliteration` for further information.
```

Fix in the backend (compile-time — which is exactly what survives Mob's missing runtime
config, §1.4c):

```elixir
use Cldr,
  precompile_transliterations: [{:latn, :arabext}],
  precompile_number_formats: ["#,##0", "#,##0.##", "#,##0.###"]
```

(`ex_cldr_numbers-2.38.3/lib/cldr/number/backend/transliterate.ex:275` iterates
`Map.get(config, :precompile_transliterations, [])` at compile time and generates a
head-per-codepoint function.) Do this on day one; retrofitting it means recompiling the
backend, which is the 4-minute step.

### 3.3 "Times and counts stay in DM Mono so columns align"

This is a **rendering** rule, not a formatting rule, and CLDR has nothing to say about it.
The design states it as: *"Times, counts and episode numbers keep DM Mono in both languages,
with Persian digits substituted, so every column still aligns."*

Two facts make this workable and one makes it fragile:

- Mob's `Text` accepts a `font:` prop resolved per-node
  (`MobBridge.kt:3473-3492`, `fontFamilyProp/2`), so you can put `font: "dm_mono"` on the
  numeral `Text` and leave the surrounding prose on Vazirmatn. Good.
- Arabic-Indic digits U+06F0–U+06F9 are a *separate block* from ASCII digits. **DM Mono does
  not contain them.** DM Mono's coverage is Latin/Latin-Ext/Cyrillic-ish; it has no Arabic
  block. So `font: "dm_mono"` + `۰۷:۳۰` will fall through to the system Arabic font on
  Android and you will lose both the mono metrics and the visual identity.
  **NOT VERIFIED by opening the font binary — verify with `fc-list`/`ttx` before committing
  to the design's rule.**
- The workable version: build a **hybrid font** (Vazirmatn's Arabic digits at DM Mono's
  advance width) or — much cheaper — use **Vazirmatn's own tabular figures**. Vazirmatn ships
  `tnum`/`ss0x` variants; a "Vazirmatn Code"/monospaced-digit cut is the normal solution in
  Persian UI work. Column alignment needs *equal advance widths*, not DM Mono specifically.

  ⚠️ Mob's `Text` has **no OpenType feature / `fontFeatureSettings` prop** — `MobText`
  (`MobBridge.kt:2268-2300`) passes `fontFamily`, `fontWeight`, `textAlign`, size, colour,
  letter-spacing and line-height, and nothing else. Selecting `tnum` therefore needs either a
  pre-instanced font file or a Compose-bridge change. Flag as a work item.

### 3.4 Strings, plurals, and "counts are interpolated, never concatenated"

The design already states the rule (design-index.md:389-392) and CLDR enforces it. Two
options, both compile-time-safe on Mob:

- **Gettext** (`{:gettext, "~> 1.0"}`) with flat keyed msgids and `.po` files per locale.
  `.po` is compiled into BEAM code at compile time — no runtime file reads, no priv, works on
  Mob unchanged. `Gettext.put_locale/2` is process-dictionary-based (same caveat as §6.4).
- **`ex_cldr_messages`** for anything with a plural or a number inside it, using ICU
  MessageFormat: `"{count, plural, one {# قسمت} other {# قسمت}} تماشا شد"`. Persian's CLDR
  plural rules give `one` for 0 and 1 and `other` otherwise — you cannot get that from
  `if n == 1`.

`ex_cldr_messages` 2.0.1 also ships an optional ICU4C MF2 NIF; it is optional and degrades
cleanly, and Mob requires all NIFs to be statically linked and registered in
`driver_tab_ios.c` (mob-framework.md:806-807) — so **do not enable the NIF**. The pure-Elixir
parser is the one that ships.

## 4. RTL on Mob — **Mob has no RTL support. At all. On either platform.**

### 4.1 The evidence

Exhaustive grep of `mob 0.7.20` (`deps/mob`, all of `lib/`, `src/`, `android/jni/*.zig`,
`ios/*.swift`, `ios/*.m`, `priv/`) for `layoutDirection`, `LocalLayoutDirection`,
`rightToLeft`, `right_to_left`, `\brtl\b`, `bidi`:

- **Zero hits** for every direction-related term. The only `bidi` match in the entire package
  is the phrase *"Bidirectional JS bridge"* in `lib/mob/webview.ex:3`.

Exhaustive grep of the generated Compose bridge
(`android/app/src/main/java/com/example/<app>/MobBridge.kt`, 3,635 lines) for
`layoutDirection|LocalLayoutDirection|Rtl|RightToLeft|absoluteOffset|Alignment.Start|Alignment.End`:

- **One hit**, and it is unrelated: `engine.setLanguage(java.util.Locale.forLanguageTag(...))`
  at line 1585 — text-to-speech.

Exhaustive grep of the SwiftUI runtime (`deps/mob/ios/MobRootView.swift`, 64.5 KB) for
`layoutDirection|rightToLeft|environment(`:

- **Zero hits.** The only `@Environment` in the file is `\.colorScheme` (line 1319).

And the generated `AndroidManifest.xml` (`android/app/src/main/AndroidManifest.xml:66-72`):

```xml
<application
    android:label="FreshMobBeam"
    android:icon="@mipmap/ic_launcher"
    android:allowBackup="false"
    android:extractNativeLibs="true"
    android:networkSecurityConfig="@xml/network_security_config"
    android:theme="@style/AppTheme">
```

**`android:supportsRtl` is absent.** Android's own documentation
(<https://developer.android.com/guide/topics/manifest/application-element>) is unambiguous:

> "If this is set to `"false"` or if `targetSdkVersion` is set to 16 or lower, the RTL APIs
> are ignored or have no effect, and your app behaves the same regardless of the layout
> direction associated to the user's locale choice. That is, your layouts are always
> left-to-right.
>
> **The default value of this attribute is `"false"`.**"

Combined with Compose's actual source
(`androidx-main/compose/ui/ui/src/androidMain/kotlin/androidx/compose/ui/platform/AndroidComposeView.android.kt:984-993`):

```kotlin
override var layoutDirection by
    mutableStateOf(
        // In Jetpack Compose, use the locale layout direction (i.e. layoutDirection came from
        // configuration) as a default layout direction.
        toLayoutDirection(context.resources.configuration.layoutDirection)
            ?: LayoutDirection.Ltr
    )
```

— Compose reads the *Configuration*, the Configuration is forced LTR without `supportsRtl`,
and nothing in Mob ever provides `LocalLayoutDirection` itself. **A Persian device running a
Mob app today renders left-to-right.** This is a native-code work item on the critical path
for 8 of the 62 screens (55–62), and it cannot be worked around from Elixir.

### 4.2 The good news: Mob's Compose renderer is already written in direction-relative terms

The fork you have to make is small, because the existing bridge happens to use `start`/`end`
rather than absolute positioning. Verified in `MobBridge.kt`:

| what | line | maps to | mirrors under RTL? |
|---|---|---|---|
| `padding_left` | 3400 | `start = …dp` | ✅ |
| `padding_right` | 3398 | `end = …dp` | ✅ |
| `align: "leading"` / `"trailing"` | 3546-3547 | `Alignment.CenterStart` / `CenterEnd` | ✅ |
| `align: "top_leading"` (default) | 3552 | `Alignment.TopStart` | ✅ |
| `text_align: "right"` | 3451 | `TextAlign.End` | ✅ (and see caveat) |
| `Row` children | 2195 | default `Arrangement.Start` | ✅ |
| `Progress` | 2467 | `LinearProgressIndicator` | expected ✅ — **NOT VERIFIED** |
| `Image` | — | Coil `AsyncImage` | ✅ never mirrors (correct) |
| `Canvas` draw ops | 2768-2860 | absolute `Offset(x, y)` px | ❌ never mirrors |
| `Icon` | 2547-2548 | `Icons.Filled.ChevronRight/Left` | ❌ never mirrors |

Caveat on `text_align`: the Mob prop is spelled `"right"` but maps to the *relative*
`TextAlign.End`. Under RTL, `text_align: "right"` will render on the **left**. That is
arguably correct but is a trap — Compose has absolute `TextAlign.Left`/`TextAlign.Right` and
Mob exposes neither. Add `"start"`/`"end"`/`"absolute_left"`/`"absolute_right"` when you fork.

### 4.3 How to do the mirroring

**Do not rely on the OS.** The design has an explicit in-app language switch (screen 53) and
a settings entry (screen 62), so direction must follow *app state*, not
`Configuration.layoutDirection` — otherwise switching language requires an Activity recreate
and cannot be previewed. Drive it from Elixir.

Three changes, all in code you already own:

1. **`AndroidManifest.xml`** — add `android:supportsRtl="true"` to `<application>`. Needed so
   the framework doesn't force-LTR the Configuration, and so `TextView`-family bits inside
   `NativeView`/`WebView` behave.

2. **`MobBridge.kt`** — wrap the render root in a provider driven by a node prop:

   ```kotlin
   val dir = when (rootNode.props["layout_direction"] as? String) {
       "rtl" -> LayoutDirection.Rtl
       else  -> LayoutDirection.Ltr
   }
   CompositionLocalProvider(LocalLayoutDirection provides dir) {
       RenderNode(rootNode, Modifier)
   }
   ```

   and, symmetrically, honour `layout_direction` on **any** node so an island can opt out:

   ```kotlin
   // inside RenderNode, before the when(node.type)
   node.props["layout_direction"]?.let { … wrap this subtree … }
   ```

   That single per-node escape hatch is what implements the design's `lock` list.

3. **`MobRootView.swift`** — the iOS equivalent is one line, `.environment(\.layoutDirection, .rightToLeft)`,
   on the root view. Same per-node override mechanism.

Then in Elixir the whole thing is one prop, exactly as the design describes it
(*"RTL is a container attribute, not a fork"*):

```elixir
~MOB"""
<Column layout_direction={@dir} padding={21}>
  …
</Column>
"""
```

### 4.4 What must **not** mirror, and how to stop it

The design's rule (design-index.md:371-372) is the right one:

> "anything that means **direction of reading** flips. Anything that means **direction of time
> or motion** — play, skip, a clock hand — does not."

| must not mirror | why it would, and the fix |
|---|---|
| **Poster / meal artwork** | Won't mirror. Compose `Image`/Coil never auto-mirrors bitmaps. ✅ free. |
| **Play / pause / skip glyphs** | `Icons.Filled.PlayArrow` etc. do **not** auto-mirror. ✅ free. Do **not** switch these to `Icons.AutoMirrored.*`. |
| **Clock and timer faces** | Drawn with `Canvas`. `DrawScope` operations use absolute pixel offsets — they never mirror. ✅ free. |
| **Star ratings, checkmarks, brand mark** | Icons/images — ✅ free. |
| **Charts with a fixed axis** | Also `Canvas`, also absolute — so they **won't** mirror even when you want them to (screen 61 wants the time axis reading right-to-left, bars filling from the right, and the pixel field starting top-right). **Mirror the data, not the renderer**: reverse the series in Elixir and emit `x` coordinates already flipped. This is the correct architecture anyway — the design's *"Most declarative chart libraries do not mirror"* (design-index.md:422) is a statement about layout engines, and you are not using one. |
| **Back / row chevrons** | These *must* mirror, and won't. Either (a) keep the design's approach — pick the glyph in Elixir (`arrow_forward_ios` in RTL, per design-index.md:75-76 and 180) — or (b) map them to Compose's `Icons.AutoMirrored.Filled.ArrowBack` / `.KeyboardArrowLeft` in `materialIconForLogical/1` (`MobBridge.kt:3500-3513`), which flip automatically. **(a) is less native but zero native work; (b) is right but needs the Kotlin fork you're already making.** Do (b). |
| **Progress bars filling from the right** | M3's `LinearProgressIndicator` is expected to honour `LocalLayoutDirection`. **NOT VERIFIED.** If it does not, the design's 2 px track is trivially two `Box`es in a `Row` with `weight`, which mirrors for certain. |
| **Poster-stack overlap direction** | Implemented with per-node offsets; `RenderNode` wraps offset nodes in an outer `Box(Modifier.offset(...))` (`MobBridge.kt:3429-3432`). `Modifier.offset(x:)` **is** direction-aware (`Modifier.absoluteOffset` is not), so it should mirror. **NOT VERIFIED.** |

For any island that must stay LTR inside an RTL screen (a chart, a code block, a URL), the
per-node `layout_direction: :ltr` escape hatch from §4.3 is the whole answer.

BiDi text itself needs no work: Compose runs the Unicode Bidirectional Algorithm, and per
JetBrains' Compose RTL guide (<https://kotlinlang.org/docs/multiplatform/compose-rtl.html>)
"Eastern Arabic numerals align naturally in RTL text". Known upstream issues listed there:
caret position with non-RTL characters in an RTL layout (CMP-3096) and caret position for
Arabic digits (CMP-2772) — relevant to `TextField` on the Persian side, worth a manual test.

### 4.5 Effort estimate

- `AndroidManifest.xml`: 1 line.
- `MobBridge.kt`: ~30 lines (root provider, per-node override, absolute text-align values,
  AutoMirrored icon map).
- `MobRootView.swift`: ~15 lines, later (Android is the priority).
- Elixir: one `layout_direction` assign threaded from `Mob.State`.

That is a day of work, not a rewrite — but it is **native** work, it lands in the forked
native shell, and per mob-framework.md:1517-1563 ("The native-shell fork problem") that fork
has no upstream upgrade path. Budget for re-applying it on every Mob bump.

### 5.3 Compile-time locale pruning — yes, and it is the default

`use Cldr, locales: ["en", "fa"]` is the pruning mechanism, and it is not optional — ex_cldr
only ships `en`, `en-001`, `und` in its own priv and downloads what you list. The
generation log confirms the scope:

```
Generating Kati.Cldr for 3 locales named [:en, :fa, :und] with a default locale named :en
```

`und` is always included (root fallback). Three locales, not 766.

Two further trims worth taking:

- **`data_dir:`** — by default ex_cldr writes the downloaded `fa.json` (607 KB) and `en.json`
  into `Application.app_dir(<otp_app>, "priv/cldr/locales")`
  (`ex_cldr-2.47.5/lib/cldr/config/config.ex:255-296`). On Mob the app's whole `priv/` is
  rsynced to the device (`native_build.ex:2220-2240`), so you would ship ~1.2 MB of JSON that
  is **only used at compile time**. Set `data_dir: "cldr_data"` on the backend to keep it out
  of `priv/`. Verified: `:data_dir` on a backend config takes highest priority.
- **`digital_token` (3.07 MB / 0.38 MB stripped)** arrives via
  `ex_cldr_currencies` ← `ex_cldr_numbers`, and is a registry of crypto-asset codes. Kati's
  money screens deal in real currencies. It is a hard dependency, so you cannot drop it, but
  it is the single largest avoidable item if you ever need the space.

### 5.4 Boot time

There is essentially **no boot-time risk with ex_cldr**, and that is a direct consequence of
the compile-time model: all data is in the `LitT` chunk of already-loaded modules. No file
I/O, no ETS build, no `:persistent_term` population, no supervisor. The cost is *module load
time* on first use, which the BEAM does lazily.

Compare Localize: `Localize.Supervisor`'s post-start work "interns every supplemental atom and
resolves the configured `:supported_locales`", plus `File.read!` + `:erlang.binary_to_term` of
`likely_subtags.etf` (460 KB), `plural_rules_cardinal.etf` (376 KB),
`collation_tailoring.etf` (512 KB), `collation_table.etf` (708 KB) — several MB of ETF decode
on the startup path, on a phone. Another point for ex_cldr on device.

⚠️ **The one real startup cost is the Persian calendar**, and §2.4 already removes it.

## 6. Device locale detection, in-app override, live re-render

### 6.1 Mob exposes no locale API. None.

`Mob.Device`'s full NIF surface (`deps/mob/src/mob_nif.erl`, extracted):

```
device_battery_state   device_foreground      device_keep_awake
device_lock_orientation device_low_power_mode device_model
device_network_state   device_orientation     device_os_version
device_set_dispatcher  device_thermal_state
```

No `device_locale`, no `device_language`, no `device_region`. Grep for `locale|i18n|language`
across all of `deps/mob` returns only TTS (`Mob.Speech`'s `:voice` BCP-47 option,
`lib/mob/speech.ex:22`) and unrelated prose. **UNKNOWN/absent — this is a documented gap, not
an inference.**

### 6.2 Recommendation: **don't detect it in v1.**

The design already solved this: **screen 53 is an explicit language chooser**
("English — LEFT TO RIGHT · 1234 · GREGORIAN" / "فارسی — RIGHT TO LEFT · ۱۲۳۴ · SHAMSI",
design-index.md:151), reachable from onboarding, and screen 62 puts the Language group
**first** in Settings. Default to English, ask once, persist the answer in SQLite via Ash.

That deletes the native work item entirely for v1 and is arguably better UX for a Persian
user with an English phone (a very common combination). Add detection later as a *default* for
the chooser, not as the mechanism.

### 6.3 If/when you do detect it

**Android** — in the Kotlin bridge you are already forking:

```kotlin
// system locale
val sys = context.resources.configuration.locales[0].toLanguageTag()   // "fa-IR"
// per-app override, API 33+
val lm = context.getSystemService(LocaleManager::class.java)
val app = lm.applicationLocales.takeIf { !it.isEmpty }?.get(0)?.toLanguageTag()
```

`minSdk` is **28** (`android/app/build.gradle:42`) and `targetSdk` **35**, so both paths are
needed: `LocaleManager` on 33+, `AppCompatDelegate.setApplicationLocales(LocaleListCompat…)`
below (AndroidX `appcompat:1.6.1` is already a dependency —
`android/app/build.gradle:121`). If you want Kati to appear in Settings → System → Languages →
App languages, add `android:localeConfig="@xml/locale_config"` with an `<locale android:name="en"/>`
+ `<locale android:name="fa"/>` list, or set `androidResources { generateLocaleConfig = true }`
(AGP 8.1+). Docs: <https://developer.android.com/guide/topics/resources/app-languages>.

⚠️ Note that `AppCompatDelegate.setApplicationLocales` **recreates the Activity**, which for a
Mob app means tearing down and re-attaching the Compose root. Prefer keeping locale in Elixir
state and only using the platform API to *read* a default.

**iOS** — `Locale.preferredLanguages.first` / `Locale.current.identifier` in
`MobRootView.swift`, surfaced through the same NIF.

Package it as a Mob plugin (`mix mob.new_plugin`) rather than editing the shell, if you can —
mob-framework.md §7 documents the plugin path for native bridges (Kotlin + NIF registration),
and a plugin survives shell regeneration better than a hand edit.

### 6.4 ⚠️ The process-dictionary trap — this one *will* bite

`Cldr.put_locale/1` stores the locale in the **process dictionary**
(`ex_cldr-2.47.5/lib/cldr.ex:265-268`):

```elixir
def put_locale(_backend, %LanguageTag{} = locale) do
  Process.put(@process_dictionary_key, locale)
  {:ok, locale}
end
```

`Gettext.put_locale/2` does the same. **Every Mob screen is its own GenServer**
(`Mob.Screen`, `screen.ex:226-232`), so a locale set in one screen is invisible to the next
one, and invisible to any `Task`/Ash parallel load. This is the same problem ash_localize
exists to solve — and you get to solve it more simply because Kati has exactly two locales.

The pattern that works on Mob:

```elixir
defmodule Kati.I18n do
  @moduledoc "Single source of truth for the active locale. Global, not per-process."

  def locale, do: Mob.State.get(:locale, :en)

  def put_locale(loc) when loc in [:en, :fa] do
    Mob.State.put(:locale, loc)
    Kati.Repo.put_setting(:locale, loc)       # survives a cold start
    broadcast_locale_change(loc)
    :ok
  end

  def direction, do: if(locale() == :fa, do: :rtl, else: :ltr)
  def calendar,  do: if(locale() == :fa, do: Kati.Calendar.Shamsi, else: Calendar.ISO)
  def first_day, do: if(locale() == :fa, do: 6, else: 1)
end
```

and then **always pass `locale:` explicitly at the call site**:

```elixir
Kati.Cldr.Date.to_string!(date, locale: Kati.I18n.locale(), format: "EEEE d MMMM y")
```

Never `Cldr.put_locale/1`. It costs one keyword per call and removes an entire class of
"why is this screen in English" bugs. It also removes the need for
`Application.put_env(:ex_cldr, :default_backend, Kati.Cldr)` — call `Kati.Cldr.*` functions
directly and `Cldr.Config.default_backend/0` (which *does* read `Application.get_env/2` at
runtime, `config.ex:382-385`) is never reached. Given §1.4c, that matters.

### 6.5 Re-rendering live screens on a locale change

Mob has no global re-render. `Mob.Theme.set/1` only writes Application env and pushes a
palette to native (`deps/mob/lib/mob/theme.ex:156-160`); the docs say it "takes effect on next
render". The framework's own precedent for reacting to an environment change is
`Mob.Theme.AdaptiveWatcher` — a singleton GenServer that subscribes to `Mob.Device` and calls
`Mob.Theme.set/1` again. Mirror that shape.

What actually re-renders:

- The currently-visible screen is registered under the atom name `:mob_screen`
  (`screen.ex:230-232`, *"Register under `:mob_screen` so C-layer `mob_handle_back()` can find
  us"*). `send(:mob_screen, {:locale_changed, loc})` → the screen's `handle_info/2` →
  `Mob.Socket.assign/3` → re-render. That is the cheap path.
- **But a locale change flips layout direction for the whole tree**, including the nav shell,
  the tab bar and every screen below the top of the stack. The honest answer is to **re-root**:

  ```elixir
  def handle_info({:locale_changed, _loc}, socket) do
    Mob.Screen.start_root(Kati.HomeScreen)
    {:noreply, socket}
  end
  ```

  The design supports this: screen 53 is an onboarding step that navigates onward
  (`→ 26`), and screen 62's Language group sits in Settings where a visible reset reads as
  intentional. A brief cross-fade is the design's own reduce-motion behaviour anyway
  ("Reduce motion → cross-fades instead of slides", design-index.md:352-353).

⚠️ Observation while reading `screen.ex`: `Process.register(self(), :mob_screen)` is called
**unconditionally in `init/1`**, so two simultaneously-alive render-mode screens would collide
on that name. That is a Mob concern rather than an i18n one, but it constrains how you
broadcast — assume **one addressable screen**, and put the durable locale in `Mob.State` +
SQLite so newly-mounted screens read it in `mount/3`.

## 7. Fonts

### 7.1 How Mob bundles them

App fonts go in `priv/fonts/*.{ttf,otf}` and are collected by
`mob_dev/lib/mob_dev/native_build.ex:4844-4852` (`collect_all_fonts/0`), then:

**Android** (`native_build.ex:4887-4918`, `apply_fonts_to_android!/0`):

> "Copies the app's + plugins' fonts into the Android `res/font/` dir under a normalised
> resource name (lowercase + underscores; the renderer normalises the `font:` prop the same
> way to look them up via `getIdentifier`). **Unlike `assets/`, `res/font/` entries are stored
> uncompressed**, which Android's font loader requires."

Resolution at render time (`MobBridge.kt:3473-3492`):

```kotlin
private fun fontFamilyProp(props: Map<String, Any?>, context: android.content.Context?): FontFamily? {
    val name = props["font"] as? String ?: return null
    if (context != null) {
        var resName = name.lowercase().replace(Regex("[^a-z0-9_]"), "_")
        if (!resName.matches(Regex("^[a-z].*"))) resName = "f_$resName"
        val resId = context.resources.getIdentifier(resName, "font", context.packageName)
        if (resId != 0) {
            try {
                val tf = androidx.core.content.res.ResourcesCompat.getFont(context, resId)
                if (tf != null) return FontFamily(tf)
            } catch (_: Exception) { }
        }
    }
    return try { FontFamily(Typeface.create(name, Typeface.NORMAL)) } catch (_: Exception) { null }
}
```

**iOS** (`native_build.ex:4861-4884`, `apply_fonts_to_ios_bundle!/2`): copies into the `.app`
bundle root and merges the basenames into `Info.plist`'s `UIAppFonts`.

Both raise on name collisions (`font_resource_collision` / `font_basename_collision`) —
worth knowing because Android collapses `-`, `_` and space to `_`, so `Vazirmatn-Bold.ttf`
and `Vazirmatn Bold.ttf` collide.

### 7.2 ⚠️ One `FontFamily` per file — so one `font:` value per weight

`FontFamily(typeface)` wraps a **single** `Typeface`. There is no weight-family construction
(`FontFamily(Font(resId, FontWeight.W400), Font(resId2, FontWeight.W700), …)`) anywhere in the
bridge. Consequences:

- `font_weight: :bold` on a `Text` with `font: "vazirmatn"` will ask Compose to *synthesise*
  bold from the loaded typeface, not to load `Vazirmatn-Bold.ttf`. Synthetic bold on Persian
  script is visibly bad — it thickens joins and closes counters.
- **Whether a variable font's `wght` axis is honoured through this path is UNKNOWN** —
  `Typeface.create(family, weight, italic)` exists from API 28 and *may* select a named
  instance, but nothing in Mob configures `FontVariationSettings`, and I did not test it on a
  device.

**Recommendation: ship static instances and address them by name.**

```
priv/fonts/
  Vazirmatn-Regular.ttf        120 KB
  Vazirmatn-Medium.ttf         120 KB
  Vazirmatn-SemiBold.ttf       120 KB
  Vazirmatn-Bold.ttf           120 KB
  Vazirmatn-ExtraBold.ttf      120 KB
  PlusJakartaSans-*.ttf        (5 weights; variable file is 172 KB)
  DMMono-Regular.ttf            49 KB
  DMMono-Medium.ttf             49 KB
```

Sizes verified from `github.com/rastikerdar/vazirmatn` (`fonts/ttf`) and
`github.com/google/fonts` (`ofl/vazirmatn`, `ofl/plusjakartasans`, `ofl/dmmono`) via the
GitHub API. Vazirmatn variable (`Vazirmatn[wght].ttf`) is **236 KB**; Plus Jakarta Sans
variable is **172 KB**.

Budget: **~1.1–1.3 MB uncompressed** for the full static set (design uses weights 400/500/600/700/800
for both sans families, plus DM Mono 400/500). If that hurts, the variable files are 236 +
172 + 98 = **506 KB** — but only if the variable path works (test it first). Remember
`res/font/` is stored **uncompressed** in the APK, so this is real download size.

### 7.3 Selecting per locale

There is no automatic per-script font fallback in Mob. Do it in the component layer:

```elixir
defmodule Kati.Type do
  def sans(:fa, :bold), do: "vazirmatn_bold"
  def sans(:fa, w),     do: "vazirmatn_#{w}"
  def sans(_,  :bold),  do: "plusjakartasans_bold"
  def sans(_,  w),      do: "plusjakartasans_#{w}"

  def mono(_locale), do: "dmmono_regular"   # but see §3.3 — DM Mono has no Arabic digits

  # design-index.md:318 — "tracking breaks the joins"; Persian rides a taller line-height
  def tracking(:fa, _), do: 0.0
  def tracking(_, :mono_label), do: 0.16
  def line_height(:fa), do: 1.4
  def line_height(_),   do: 1.5
end
```

Wrap it once in a `<KatiText>` composite (Mob composites are pure Elixir —
`Mob.Composite.register/2`, as the sample app does for `mishka_drawer`) so no screen ever
picks a font by hand. That is the "no manual work" answer here: one component, 62 screens.

⚠️ **Material Symbols Rounded** (673 icon spans in the design) is a *fourth* font. Mob's icon
path uses `androidx.compose.material.icons` vectors, not a symbol font
(`MobBridge.kt:3500-3513`, `materialIconForLogical/1`, currently 10 mapped names with a
fallback to a visible `Star`). You will either extend that map substantially or ship
Material Symbols as a font and render icons as `Text` with a codepoint. The latter gets you
`font-variation-settings: 'FILL' 1` (which the design uses) — but see §7.2: variable axes
through Mob's font path are UNKNOWN.

### 8.3 The Shamsi calendar

```elixir
defmodule Kati.Calendar.Shamsi do
  @moduledoc """
  Persian (Solar Hijri) calendar for display only.

  Same results as `Cldr.Calendar.Persian` (verified: 0 mismatches over 1826
  consecutive days) but ~380x faster, because Nowruz is a precomputed table
  rather than a per-call astronomical computation. Regenerate the table with
  `mix kati.gen.nowruz`.
  """

  use Cldr.Calendar.Behaviour,
    epoch: ~D[0622-03-20 Cldr.Calendar.Julian],
    cldr_calendar_type: :persian

  # Gregorian year => ISO day number of Nowruz. Generated, do not hand-edit.
  @nowruz %{2000 => 730_565, 2001 => 730_930, 2002 => 731_295, 2003 => 731_660,
            2004 => 732_025, 2005 => 732_391, 2006 => 732_756, 2007 => 733_121
            # … through 2100
          }

  @impl true
  def leap_year?(year),
    do: date_to_iso_days(year + 1, 1, 1) - date_to_iso_days(year, 1, 1) == 366

  def date_to_iso_days(year, month, day) do
    ny = Map.fetch!(@nowruz, year + 621)
    ny - 1 + if(month <= 7, do: 31 * (month - 1), else: 30 * (month - 1) + 6) + day
  end

  def date_from_iso_days(iso_days) do
    {gy, _, _} = Cldr.Calendar.Gregorian.date_from_iso_days(iso_days)
    {ny, year} =
      if Map.fetch!(@nowruz, gy) <= iso_days,
        do:   {Map.fetch!(@nowruz, gy),     gy - 621},
        else: {Map.fetch!(@nowruz, gy - 1), gy - 622}

    doy = iso_days - ny + 1

    if doy <= 186,
      do:   {year, div(doy - 1, 31) + 1,   rem(doy - 1, 31) + 1},
      else: {year, div(doy - 187, 30) + 7, rem(doy - 187, 30) + 1}
  end
end
```

*(The `@nowruz` values above are real, taken from the verification run. `Map.fetch!` is
deliberate: a date outside the generated range should crash loudly in dev, not silently
produce a wrong year. Generate 1300–1600 SH and you have ~300 integers covering three
centuries.)*

### 8.4 The formatting facade

```elixir
defmodule Kati.Fmt do
  @moduledoc "Every user-visible number, date and time goes through here."

  alias Kati.I18n

  # "یکشنبه ۲۵ مرداد ۱۴۰۵"  /  "Sunday 16 August 2026"
  def long_date(%Date{} = d, loc \\ nil) do
    loc = loc || I18n.locale()

    d
    |> to_display_calendar(loc)
    |> Kati.Cldr.Date.to_string!(locale: loc, format: "EEEE d MMMM y")
  end

  # "۱٬۴۸۰"  /  "1,480"
  def number(n, loc \\ nil),
    do: Kati.Cldr.Number.to_string!(n, locale: loc || I18n.locale())

  # "۱۸٪"  /  "18%"
  def percent(f, loc \\ nil),
    do: Kati.Cldr.Number.to_string!(f, locale: loc || I18n.locale(), format: :percent)

  defp to_display_calendar(d, :fa), do: Date.convert!(d, Kati.Calendar.Shamsi)
  defp to_display_calendar(d, _),   do: d
end
```

Worked example, with **verified** outputs:

```elixir
iex> Kati.I18n.put_locale(:fa)
iex> Kati.Fmt.long_date(~D[2026-08-16])
"یکشنبه ۲۵ مرداد ۱۴۰۵"

iex> Kati.Fmt.number(1480)
"۱٬۴۸۰"

iex> Kati.Fmt.percent(0.18)
"۱۸٪"

iex> Kati.I18n.put_locale(:en)
iex> Kati.Fmt.long_date(~D[2026-08-16])
"Sunday 16 August 2026"
```

⚠️ **Use the explicit pattern `"EEEE d MMMM y"`, not `format: :full`.** CLDR's `fa` +
`persian` `full` pattern is `"y MMMM d, EEEE"` (year first), which renders
`"۱۴۰۵ مرداد ۲۵، یکشنبه"` — *not* the design's string. Verified both ways:

```
fa full:                    "۱۴۰۵ مرداد ۲۵، یکشنبه"
fa "EEEE d MMMM y":         "یکشنبه ۲۵ مرداد ۱۴۰۵"     ← the design's string
en full (persian calendar): "Sunday, Mordad 25, 1405 AP"
```

(The `fa` **Gregorian** `full` pattern *is* `"EEEE d MMMM y"` — the two calendars disagree
inside the same locale. Easy to trip over.)

## 9. Open questions / not verified

Stated plainly so nothing here is mistaken for a measurement.

1. **Does `config/config.exs` reach a Mob device?** Static evidence says no (no `env` in the
   `.app`, no `sys.config` generation, no `loadconfig` at deploy). Confirm with a one-line
   `Application.get_env(:mob, :repo)` probe on device before designing around it. Everything
   in §8 is written to be correct either way.
2. **Does M3 `LinearProgressIndicator` mirror under `LayoutDirection.Rtl`?** Expected yes,
   untested. Fallback (two `Box`es in a `Row`) is certain.
3. **Does `Modifier.offset(x:)` mirror in Mob's poster-stack path?** It should
   (`absoluteOffset` is the non-mirroring one); untested.
4. **Do variable fonts work through `ResourcesCompat.getFont` → `FontFamily(Typeface)`?**
   Unknown. Ship static instances until proven.
5. **Does DM Mono contain U+06F0–U+06F9?** Almost certainly not — verify before committing to
   the design's "numerals stay mono" rule as literally DM Mono. Vazirmatn tabular figures are
   the likely correct answer.
6. **Is there a working timezone database on device?** No tz package appears in the Mob
   dependency tree and `Mob.Device` has no timezone API. §2.6 depends on this.
7. **Does the Android release path strip the app's own dep beams** (as opposed to only the OTP
   runtime libs)? `strip_release/1` walks the whole staging tree and `copy_app_beams/2` writes
   into it, so it should — but measure `otp.zip` before/after adding the CLDR deps.
8. **Localize CDN**: `https://elixir-localize.com/locales/v1.2.0/fa.etf` → 404 today. If you
   ever revisit Localize, this needs to be resolved with upstream first.
9. **`ex_cldr_calendars_persian` has 1,808 lifetime downloads.** Treat every output as
   suspect until checked against a published Iranian calendar table. The leap-year list and
   the 2026-08-16 → 1405-05-25 conversion in this document both check out; that is two data
   points, not a test suite. Write property tests over a decade of dates.
