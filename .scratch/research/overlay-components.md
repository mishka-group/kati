## 0. TL;DR — the one thing that changes every decision

**There are three different Android renderers in play, and they are not the same program.**

1. **`development/mob/android/app/src/main/java/com/example/mishka_mob/MobBridge.kt`** — 4607 lines.
   The Mishka dev app's own hand-written Compose renderer. **This is where `:anchored` lives**
   (`MobAnchored`, `MobBridge.kt:2471`; dispatch arm `MobBridge.kt:2436`; position provider
   `MobBridge.kt:2610`). Added by Mishka in commit `2cd3a427` *"Add an `anchored` node type: real
   overlays, proven on device"*.
2. **`mob_new`'s template** — `priv/templates/mob.new/android/app/src/main/java/MobBridge.kt.eex`,
   3635 lines. **This is what a `mix mob.new` app — i.e. Kati — actually gets.**
   `grep -in "anchored\|Popup"` on it returns **zero hits.**
3. **The published `mob` hex package** — `deps/mob/` ships `ios/` (full SwiftUI renderer),
   `android/jni/*.zig` (JNI only, **no Compose renderer**), `src/`, `priv/tags/`, `lib/`.
   `grep -rn -i anchored deps/mob/ios deps/mob/android` → **nothing**.

Mishka states this itself, in its own gap ledger — `development/mob/IOS_TODO.md:340-341`:

> "Bridge fixes made in `MobBridge.kt` here do **not** reach consumers: apps generated by
> `mix mishka.ui.gen.mob` get the mob templates, not this file."

and again in `usage-rules/mob/slider.md:95-96`:

> "Note also that bridge fixes made here do not reach apps generated by `mix mishka.ui.gen.mob` — those
> get the mob templates, not this repo's `MobBridge.kt`."

### The consequence, stated precisely

`RenderNodeInner` in the `mob_new` template ends with a `when (node.type) { … }` **used as a statement,
with no `else` arm** (`MobBridge.kt.eex:2175` function head, `:2188` the `when`, `:2255-2258` the last
arms and closing brace). In Kotlin a statement-`when` on a `String` needs no exhaustiveness. So:

> **In a freshly generated Mob app on Android, a `%{type: :anchored}` node renders NOTHING —
> not the panel, and not the trigger either, because the trigger is that node's child.**

On iOS the failure is different and milder: `mob_nif.m`'s `mob_node_from_dict` maps the type string
through an `if`/`else if` chain (`deps/mob/ios/mob_nif.m:604-648`) that ends at `"gpu_view"` with **no
`else`**, leaving `node.nodeType` at its zero-initialised value — which is `MobNodeTypeColumn`
(`deps/mob/ios/MobNode.h:22`, first member of the enum). So an anchored node on iOS degrades to a
stacked `VStack` of `[trigger, panel]` — the accordion the node type was invented to replace.

**So `:anchored` works in exactly one place on earth: Mishka's own showcase app.** It is Android-only
*there*, and Android-**nowhere** in a generated app.

### Which components emit `:anchored`

Only **three**: `popover`, `tooltip`, `preview_card`. The generator says so itself
(`lib/mishka_chelekom/generators/mob.ex:40-42`):

> "`anchored` is one of these rather than a component: it builds the `:anchored` node that popover,
> tooltip and preview_card all place their panel in, and a generated popover will not compile without
> it."

Verified by grepping the source of truth — `Anchored.anchor(` / `Anchored.closed(` appear only in
`mishka_popover.ex:309-310`, `mishka_tooltip.ex:182,186`, `mishka_preview_card.ex:315,320`.

**⚠️ The catalog over-reports this.** Ten more catalogs carry `kit: ["anchored"]` —
`drawer`, `menu`, `menubar`, `navigation_menu`, `combobox`, `select`, `tree_select`, `context_menu`,
`autocomplete`, `color_input`. **They are false positives.** `Mob.kit_dependencies/1`
(`lib/mishka_chelekom/generators/mob.ex:163-171`) matches the *string* `MishkaMob.Components.Anchored`
anywhere in the source file — **including moduledoc prose**. Every one of those ten only *mentions*
`Anchored` in a paragraph explaining why it does **not** use it (e.g. `mishka_menu.ex:15`
"The menu has not been moved onto it"; `mishka_drawer.ex:20-24`; `mishka_select.ex:10`;
`mishka_menubar.ex:17-19`). Their node trees contain no `:anchored`.

So: **generating `select` or `menu` costs you a spurious `anchored.ex` file in
`lib/kati/components/`, and nothing else.** Do not let the catalog scare you off them.

### Second Android-only gap, less obvious

`on_long_press` is registered by the published renderer (`deps/mob/lib/mob/renderer.ex:356-357`) and
implemented on iOS (`deps/mob/ios/MobRootView.swift:70-71`, `.onLongPressGesture(minimumDuration: 0.5)`;
`deps/mob/ios/mob_nif.m:854-857`). On Android it is implemented **only** in Mishka's dev bridge
(`combinedClickable`, `MobBridge.kt:2313-2346`, added in commit `f52b2d34`). The `mob_new` template has
**zero** occurrences of `on_long_press` or `combinedClickable`.

⇒ In a fresh Kati Android build, **`context_menu`'s long-press trigger, `popover`'s `open_on_hold`,
`preview_card`'s `on_hold`, and `tooltip`'s long press are all dead** — the node renders, the handler
never fires.

### Third: Mob has no modal presentation at all

The whole navigation API is `Mob.Socket` (`deps/mob/lib/mob/socket.ex:129-186`):
`push_screen/3`, `pop_screen/1`, `pop_to/2`, `pop_to_root/1`, `reset_to/3`, `switch_tab/2`.
**There is no `present_modal`, no `present_sheet`, no modal stack.** A "modal that closes rather than
pushes" is not a framework concept in Mob 0.7.20. It is either (a) a pushed screen you `pop_screen`, or
(b) an in-screen fill overlay stacked in the screen's root `:box`.

### 2.1 `dialog` — ✅ FRESH-OK, the safest modal primitive

**(a) Renders** (`mishka_dialog.ex:356-421`): while `open`, a fill `:box` stacking
`[scrim, centred-panel]`; while closed, the `<MishkaDialogTrigger>` slot or `~MOB(<Column />)`.
Node types: `:box :column :row :text :button :spacer`. **No `:anchored`.**

```
box   fill_width fill_height          ← <id>-open   (exists only while open)
├── box  fill · background=scrim      ← <id>-backdrop-modal | -backdrop-plain, on_tap=close
└── box  fill · align=:center · padding=inset
    └── box  width=320 · corner_radius ← <id>-panel, on_tap=:__mishka_dialog_ignore
        └── column padding
            ├── column ← <id>-title / <id>-description
            ├── column ← <id>-content
            └── column ← <id>-footer  (Row; ≥2 actions get weight:1 boxes)
```

**(b)** FRESH-OK on Android and iOS. Only primitives. (`corner_radius` clips on a width-locked `Box` on
both platforms — the moduledoc calls this a deliberate repeat of a Drawer lesson,
`mishka_dialog.ex:10-18`.)

**(c) Props** (`mishka_dialog.ex:141-157`): `id` `open` `modal`(`true`/`false`/`"trap-focus"`)
`title` `description` `actions` `dismissible` `on_close` `on_open_change` `width`(320) `background`(`:surface`)
`corner_radius`(`:radius_lg`) `padding`(`:space_lg`) `inset`(`:space_lg`) `scrim_color`(`0x99000000` modal /
`0x00000000` plain).
**Events:** `on_close` → `{:tap, tag}`; `on_open_change` → `{:tap, {tag, false}}` (`on_close` wins,
`:552-558`). Trigger: `on_tap` → `{:tap, tag}`, or `on_open_change` → `{:tap, {tag, true}}` (`:562-568`).
**Slots:** `<MishkaDialogTitle> <MishkaDialogDescription> <MishkaDialogFooter> <MishkaDialogTrigger>`,
each with a builder twin (`title/1 description/1 footer/1 trigger/3`) producing the identical node.
**Test tags:** `<id>-open · -backdrop-modal|-backdrop-plain · -panel · -title · -description · -content ·
-footer · -trigger|-trigger-disabled`.
**Host requirement:** the panel routes stray taps to `:__mishka_dialog_ignore` (`:196`), so the screen
**must** have `def handle_info(_msg, s), do: {:noreply, s}` or it crashes.
**Not ported** (`:159-164`): `close_on_escape` (Mob registers no key/back event), `initial_focus`,
`final_focus`, `labelledby`, `describedby`, the nine `*_class` attrs, `on_open_change_target`.

**(d) True modal sheet?** **Yes, as a centred card** — presents over content, dismisses on backdrop tap,
absorbs taps behind it. **Not** as an edge-anchored sheet: the panel is width-locked at 320 and centred.
For Kati's 06/18/31/33/46 (full-bleed sheets with a centred title bar) it is the wrong shape as shipped,
but the *mechanism* is exactly right and every piece is prop-driven.

**(e) Fresh app:** works with no native work. Two placement rules
(`mishka_dialog.ex:104-114`): the node must sit **in the screen's root `:box`** (or a root non-scrolling
`Column`) — *"the overlay is a fill node and a fill node inside a scroll has no bounded height to fill"* —
and when the opener lives inside a scrolling page, use `trigger/3` separately and tie the two with `id`.

### 2.2 `alert_dialog` — ✅ FRESH-OK

**(a)** A thin wrapper over `dialog` (`mishka_alert_dialog.ex:1-31`) with `dismissible` forced `false`
and `modal` forced `true`. Its own node contribution is a `:button` per `<MishkaAlertDialogAction>`.
No `:anchored`.

The one genuinely native insight (`:21-30`): *"a Compose Box with a background but no pointer input paints
over the page without consuming a single touch"* — so this wrapper gives the inert backdrop a handler that
**goes nowhere**, which is what makes it modal rather than merely dim.

**(b)** FRESH-OK both platforms.
**(c)** Everything `dialog` takes minus `dismissible` and `modal`. Slot `<MishkaAlertDialogAction text id
variant on_tap close>`, variants `:neutral :primary :danger`; builder `action/2`. Reuses
`<MishkaDialogTitle> <MishkaDialogDescription> <MishkaDialogFooter>` verbatim — *"an alert dialog is a
dialog, so its title is the dialog's title"* (`:53-56`). Action tags win over the `actions:` prop.
**(d)** A confirmation modal, not a content sheet. Right for Kati's destructive confirms; wrong for 06/18/31/33/46.
**(e)** Nothing. `necessary: ["dialog"]` pulls dialog in automatically.

### 2.3 `drawer` — ✅ FRESH-OK · **the only shipped bottom sheet**

**(a) Renders** (`mishka_drawer.ex:615-703`): while open, a fill `:box` = `[scrim, positioner]`; the
positioner is a `Row`/`Column` split by a `weight: 1` `:spacer` that pushes the panel to its edge.
While closed: the `<MishkaDrawerTrigger>` slot, or the edge swipe patch, or nothing.
Node types: `:box :column :row :spacer :text :button :canvas`. **No `:anchored`** — despite the catalog's
`kit: ["anchored"]` (prose false positive, `mishka_drawer.ex:20-24`, which explicitly says the stacked
Box *"is still the right shape here even though anchored overlays now exist … and unlike the anchored node
it works on both platforms"*).

```
box  fill_width fill_height                    ← <id>            (open only)
├── box  fill · background=scrim_color         ← <id>-scrim      on_tap = close | absorb
└── column fill_height                          the positioner (bottom side)
    ├── spacer weight=1                         taps fall through to the scrim
    └── column fill_width [+height=snap]       ← <id>-panel      on_tap = absorb
        ├── canvas 160×40  the drag handle     ← <id>-handle, <id>-snap-<n>
        ├── row  title + description + ✕       ← <id>-title, <id>-description, <id>-close
        ├── …your children…
        └── column                             ← <id>-footer
```

**(b)** FRESH-OK both platforms. `:canvas` is dispatched in the fresh template
(`MobBridge.kt.eex:2256`) and on iOS (`mob_nif.m:645-646`).
Mishka reports it **verified on device**: *"Verified on Android (Samsung A55, One UI / Android 15) — all
four sides anchor correctly, side panels fill height, top/bottom sheets are content-height, backdrop taps
dismiss … Also source-verified against the iOS renderer (`MobRootView.swift`)"* (`mishka_drawer.ex:211-217`).

**(c) Props** (`mishka_drawer.ex:153-178`):
`open` `id` `side`(`:left :right :top :bottom`, default `:right`) `size`(`:xs`240 `:sm`256 `:md`288
`:lg`320 `:xl`384 — width, left/right only) `title` `description` `header`(true) `handle`(false)
`handle_color`(ARGB int, **not** a token — canvas ops take ints, `:281-285`) `scrim`(true)
`scrim_color`(`0x99000000`) `dismissible`(true) `background`(`:surface`) `padding`(`:space_lg`)
`corner_radius`(none) `snap_points`([]) `snap` `extent` `snap_sequential`(false) `threshold`(64)
`swipe_direction` `swipe_area`(false) `on_close` `on_swipe`.
**Events:** `on_close` → `{:tap, tag}` (backdrop **or** ✕); `on_swipe` → `{:drag, tag, payload}`.
**Helpers:** `swipe/3` (the screen folds the gesture — a composite is stateless), `snap_heights/1`,
`snap_index/1`, `trigger/2`, `footer/1`.
**Slots:** `<MishkaDrawerTrigger>` `<MishkaDrawerFooter>`.
**Test tags:** `<id> · -scrim · -panel · -title · -description · -close · -footer · -handle ·
-swipe-area · -snap-<n>`.
**Host requirement:** catch-all `handle_info/2` — stray panel taps route to `:__mishka_drawer_ignore`
(`:141-149`, `:263`).
**Not ported** (`:228-237`): `close_on_escape` (`Mob.Screen` intercepts `{:mob, :back}` before any screen
clause and pops the nav stack, so a drawer cannot claim back), focus trapping, `modal="trap-focus"`, the
iOS page-indent, `aria-*`, `*_class`.

**(d) True modal sheet? — YES.** `side: :bottom` + `scrim: true` + `corner_radius: :radius_lg` +
`header: false` is precisely "a sheet that presents over content and dismisses". It is the **only**
component in the set that is a bottom sheet.
**Two honest caveats:**
1. **The panel does not follow the finger** (`:58-67`). It settles on release. The reason is measured, not
   lazy: a canvas reports canvas-local coordinates, so re-rendering the panel at a new height moves the
   handle canvas under the finger — *"a ruler sliding along with what it is measuring"*. Mob also has no
   animation, so there is nothing to interpolate.
2. The overlay sits **inside** the top safe-area inset (`:224-226`) — the panel starts below the status
   bar, not under it.

**(e) Fresh app:** works today, zero native work. Must live in the screen's root `:box`
(`usage-rules/mob/drawer.md:24-25`: *"Put it in the screen's root `box`, alongside your page content — a
composite cannot portal itself anywhere"*). For a fully custom look the library's own prescription is
props + children, not a fork (`mishka_drawer.ex:195-209`):

```elixir
%{type: :mishka_drawer,
  props: %{open: @open, side: :bottom, header: false,
           background: :surface_raised, corner_radius: :radius_lg,
           scrim_color: 0x66000000, padding: :space_xl, on_close: :close_sheet},
  children: [my_custom_header(assigns), my_rows(assigns)]}
```

### 2.4 `popover` — ❌ DEV-ONLY (emits `:anchored` **open *and* closed**)

**(a)** `mishka_popover.ex:307-315`:

```elixir
inner =
  case {trigger, panel} do
    {[t], [p]} -> [Anchored.anchor(t, p, anchor_opts(props, side, align))]
    {[t], []}  -> [Anchored.closed(t, anchor_opts(props, side, align))]
    # Pinned open with no trigger: there is nothing to anchor TO, so the
    # panel simply renders in place. This is the `menu`-in-a-drawer case.
    {[], [p]}  -> [p]
    {[], []}   -> []
  end
```

**Note the second clause.** `Anchored.closed/2` still builds `%{type: :anchored, …}` with one child
(`anchored.ex:120-122`). So a **closed** popover is an anchored node too — and in a fresh Android app it
renders nothing at all, taking the *trigger* with it. This is the single most dangerous line in the set.

**The fourth-clause escape hatch is real and useful:** a popover with **no trigger** and `open: true`
returns `panel/2`'s plain `:box`/`:column` — **FRESH-OK**. That is how `menu` gets its shell.

**(b)** DEV-ONLY. Android fresh app: nothing renders. iOS: degrades to a `Column` of `[trigger, panel]`
— *"the panel taking room rather than drawing over the page, and appearing below the trigger whatever the
`side`"* (`usage-rules/mob/popover.md:174-181`).

**(c) Props** (`mishka_popover.ex:123-149`): `id` `open` `trigger` `on_open_change` `open_on_hold`(false)
`disabled` `chevron`(true) `side`(`:bottom`) `align`(`:start`) `side_offset`(8) `align_offset` `flip`(true)
`clamp`(true) `edge_padding`(8) `title` `description` `close` `arrow`(false) `width` `background`(`:surface`)
`color`/`muted_color` `corner_radius`(`:radius_md`) `padding`(`:space_md`) `border_color`(`:border`)
`border_width`(1) `offset_x`/`offset_y`.
**Events:** `on_open_change` → `{:tap, {tag, next_open?}}` — one clause serves the trigger tap, the
outside tap and the close button (`:320-328`). `open_on_hold` wires `on_long_press` (dead on fresh Android).
**Slots:** `<MishkaPopoverTrigger> <MishkaPopoverTitle> <MishkaPopoverDescription> <MishkaPopoverClose>
<MishkaPopoverArrow>` + builders `trigger/1 title/1 description/1 close/1 arrow/0`.
**Public shell:** `panel/2` — this is what `menu` and `preview_card` build on.
**Test tags:** `<id>-trigger-open|-trigger-closed · -panel · -title · -desc · -close · -arrow`.
**Not ported** (`:155-165`): `modal` and its backdrop (*"a scrim belongs to whatever owns the screen root
— use dialog or drawer when the page must be blocked"*), `dismissible`, `close_on_escape`,
`initial_focus`/`final_focus`, `labelledby`/`describedby`, `open_on_hover`/`delay`/`close_delay`, `*_class`.

**(d) Modal sheet?** No, and deliberately so — no backdrop, no page blocking. It is an anchored panel.
**(e) Fresh app:** requires porting `MobAnchored` + `MobAnchoredPositionProvider` +
`rememberRealDisplaySizePx` from `MobBridge.kt:2436-2660` (~230 lines of Kotlin, plus 16 new
`androidx.compose` imports at `MobBridge.kt:208-223`) into Kati's own bridge — **and iOS still has nothing**
(`IOS_TODO.md:271-332` describes the required `anchorPreference` + root-overlay approach; the blocker at
`:325-332` is that *"the anchored primitive has to land upstream in `mob` itself"*).

### 2.7 `menu` — ✅ FRESH-OK

**(a)** `mishka_menu.ex:185` — `MishkaPopover.panel(Map.put_new(props, :padding, 6), rows(children, props))`.
`panel/2` alone: `:box :column :row :text :spacer`. **No `:anchored`** — the moduledoc says so in as many
words (`:14-17`): *"The menu has not been moved onto it, and it keeps the full-width shell it always had."*
Rows are tappable **boxes**, not Buttons — *"a Material Button centres its label, and a menu reads from the
leading edge"* (`:20-23`).
**(b)** FRESH-OK both platforms.
**(c)** `open` `on_select` → `{:tap, {tag, item_id}}` · `width` · `danger_color`(`0xFFDC2626`) + everything
`popover` accepts. Slots/builders: `item/3` (`:disabled :danger :icon :test_id`; `:id` is the *event* tag,
`test_id` is the native testTag), `separator/0`, `label/1`, `checkbox/3`, `radio/4`, submenu (indent 16).
Tags: `<MishkaMenuItem> <MishkaMenuLabel> <MishkaMenuSeparator> <MishkaMenuCheckbox> <MishkaMenuRadio>
<MishkaMenuSubmenu>`.
**Not ported** (`:38-43`): `side`, `align`, offsets, `open_on_hover`, `delay`, `id`/`*_class` — *"a menu is

## 4. Kati's five modal screens

`design-index.md:65-67`:

> **Modals** (5): 06 Add a title, 18 Quick add, 31 Event detail & edit, 33 Rating & review, 46 Swap a meal.
> All use a centred title with a leading `close` glyph; 31 and 33 add a trailing text action ("Save").
> No modal shows a tab bar or a back pill.

and the rule at `design-index.md:48`:

> "Large title, left-aligned, on every screen. **Centred titles are reserved for modals, which close rather
> than go back.**"

### What "modal" can mean in Mob 0.7.20

| Mechanism | How | Trade-off |
|---|---|---|
| **A pushed screen that pops** | `Mob.Socket.push_screen/3` on open, `pop_screen/1` on the ✕ | Full screen, own `mount/3`, own process, own scroll. **But** the transition is a *push* (a slide-in from the trailing edge), not a *present* — Mob offers no modal presentation style at all (`socket.ex:129-186`). Visually you cannot tell it apart because Mob has no transition customisation either. |
| **A fill overlay in the root `:box`** | `drawer side: :bottom`, or `dialog` | Genuinely presents over content. Same screen process, same assigns. Backdrop dismiss for free. **But** the content lives in the parent screen's `render/1` and shares its assigns. |
| **`Mob.Alert.action_sheet/2`** | `deps/mob/lib/mob/alert.ex:79-88` — native `UIAlertController(.actionSheet)` / Android list dialog | Real native sheet, real modality, **zero** content control — a title and a list of labelled buttons, nothing else. Result arrives as `{:alert, action_atom}`. |

**The design does not settle which of the first two Kati wants.** `design-index.md` describes 06/18/31/33/46
as *screens* (numbered among the 62, with the same scroller recipe as pushed screens), whose distinguishing
marks are a **centred title, a leading `close`, no tab bar, no back pill**. That is a chrome contract, not
a presentation contract. **UNKNOWN / undocumented:** whether the design intends partial-height sheets. The
only supporting hint is the `26px` "sheet" radius in the measured radii list (`design-index.md:328`), which
is not tied to a specific screen.

**Practical reading:** 31 (event detail & edit) and 33 (rating & review) are dense, scrollable, form-shaped —
they read as full-screen. 46 (swap a meal) and 06 (add a title) are list-shaped and could be either.
18 (quick add) is a single input with a preview card — the classic partial sheet.

## 5. Conclusion — the shortest correct path

### 5.1 The modal bottom sheet: **use `drawer` as-is, `side: :bottom`, `header: false`**

This is the shortest correct path and there is no close second.

- It emits **only** primitives that both the fresh Android template and the published iOS renderer
  dispatch (`:box :column :row :spacer :text :button :canvas`).
- Mishka has **run it on a real Android device** (`mishka_drawer.ex:213-217`).
- It already carries scrim, tap absorption, backdrop dismiss, drag handle, snap points, swipe-to-dismiss,
  edge swipe-in, footer, and per-part test tags.
- Its own moduledoc prescribes props + children — not a fork — for a bespoke look
  (`mishka_drawer.ex:195-209`), which is exactly the headless/unstyled discipline the owner wants: **the
  chrome props and children carry Kati's design; the component carries only mechanics.**

Kati shape:

```elixir
def render(assigns) do
  %{type: :box, props: %{fill_width: true, fill_height: true}, children: [
    page(assigns),
    %{type: :kati_drawer,
      props: %{open: assigns.sheet, side: :bottom, header: false,
               corner_radius: 26,                       # design-index.md:328 — "sheet 26"
               background: 0xFFFBFAF8, scrim_color: 0x66000000,
               padding: 0, on_close: :close_sheet},
      children: [modal_header(assigns), sheet_body(assigns)]}
  ]}
end
def handle_info(_msg, s), do: {:noreply, s}   # REQUIRED — drawer routes stray taps to an ignored tag
```

`modal_header/1` is **Kati's** — centred title, leading `close`, optional trailing "Save". That is
precisely the piece the design specifies and the piece Mishka should not own.

**For 31 and 33 (dense, form-shaped, full-screen):** push a screen and `pop_screen/1` from the ✕. Nothing
in Mob makes a full-screen `drawer` better than a pushed screen, and a pushed screen gets its own process,
its own `mount/3`, and its own scroll — which a 20-field event editor wants.

⚠️ **Do not fight the finger-tracking gap.** The panel settles on release
(`mishka_drawer.ex:58-67`). The Kati design declares **zero** transitions, animations or transforms
anywhere in 825 KB (`design-index.md:351-353`, `:438`), so this costs nothing here.

### 5.2 The anchored popover / menu on Android: **do not use `:anchored`. Use a bottom `drawer` + `menu`.**

Three options, honestly ranked:

**Option A — bottom sheet menu (recommended).** `drawer side: :bottom` + `menu` inside it.
Cost: **zero native work, zero new components.** Both Mishka moduledocs prescribe exactly this
independently — `mishka_menu.ex:9-12` (*"inside a MishkaDrawer for a bottom-sheet action list, which is
often the better phone idiom anyway"*), `mishka_context_menu.ex:29-30`, `usage-rules/mob/select.md:22-25`.
It is also the platform-correct idiom: Android's Material bottom sheet, not a desktop dropdown.

**Option B — port `MobAnchored` into Kati's bridge.** Cost: ~230 lines of Kotlin
(`MobBridge.kt:2436-2660`) + 16 imports (`:208-223`), copied into Kati's scaffolded `MobBridge.kt`.
What it buys: real anchored popovers on Android only.
What it costs beyond the copy:
- **Permanent merge debt.** Mob's own guide (<https://mob.hexdocs.pm/troubleshooting.html>, quoted in
  `mob-framework.md:1521-1524`) says *"Mob ships zero host-app Kotlin / Swift today; every app's
  `MobBridge` is its own diverged copy"*, and there is **no `mix mob.upgrade`** and no bridge-diff task.
  Every custom widget is permanent cost.
- **iOS still has nothing**, and cannot get it from Kati: `deps/mob/ios` is checksum-locked in `mix.lock`
  (`IOS_TODO.md:325-332`). The fix must land upstream in `mob`.
- **You lose the guardrail.** In Kati, `Mob.ScreenCase.assert_renderable/2` bakes `@renderable_types`
  from `deps/mob/priv/tags/{ios,android}.txt` (`deps/mob/lib/mob/screen_case.ex:96-114`). Mishka's dev app
  writes `Anchored` into both files from its own `@native_tags` fence (`development/mob/mix.exs:100-107`)
  so its tests pass; the **Chelekom generator does not** — `Registry.whitelist/2` writes only catalog
  composite tags, and kit modules are not in the catalog. So Kati's test suite would **correctly flunk**
  any popover node — a real signal you would then be tempted to suppress.

**Option C — a Mob plugin / `Mob.Component` native view.** `native_view` **is** in the fresh template
(`MobBridge.kt.eex:2136-2160, 2255`) and on iOS (`mob_nif.m:641-642`), and `Mob.Component`
(`deps/mob/lib/mob/component.ex:1-66`) is the sanctioned escape hatch — the one thing
`mob-framework.md:1578` recommends over editing `MobBridge` directly.
**But it cannot host a modal sheet or an anchored panel.** `Mob.UI.native_view/2` builds
`%{type: :native_view, props: …, children: []}` (`deps/mob/lib/mob/ui.ex:122-124`) — **children is
hardcoded empty**, and `render/1` returns a *props map*, not nodes (`component.ex:27-31`). A native view is
a leaf. You could not put Elixir-rendered rows inside it. Rejected for this purpose.

### 5.3 On the headless constraint

The owner's rule — *Mishka components stay headless and unstyled; all styling lives in Kati* — is
**not currently true of the Mob layer**, and this matters for the plan.

Mishka Mob components bake semantic tokens as defaults: `dialog` hardcodes `width: 320`,
`background: :surface`, `corner_radius: :radius_lg`, `scrim_color: 0x99000000`
(`mishka_dialog.ex:406-408`, `:197`); `drawer` hardcodes `@scrim 0x99000000`, `@pill_ink 0xFF9CA3AF`,
`@sizes %{xs: 240, …}` (`mishka_drawer.ex:254-285`); `tooltip` hardcodes `0xFF111827`
(`mishka_tooltip.ex` props table). Some values are not even prop-overridable — `mishka_dialog.ex:430` and
`:432` hardcode `<Spacer size={6} />` and `<Spacer size={16} />`.

Two facts make this workable:
1. **The generated files are vendored into Kati** (`lib/kati/components/*.ex`), not a dependency
   (`mishka-mob-index.md` §3.3, `mishka.ui.gen.mob.ex:232-240`). Editing them is supported.
2. **A regeneration silently reverts your edits** (`on_exists: :overwrite`). So: generate **once**, with
   `--module-prefix kati_`, then own the files and never regenerate that namespace.

Since almost every value Kati needs is already a prop, the realistic discipline is: set a
`Kati.BrandTheme` (`Mob.Theme` — `deps/mob/lib/mob/theme.ex:85-133`), pass the rest per call site, and
treat the vendored component files as Kati source.

### 5.4 What to generate for Kati, and what to skip

**Generate:** `drawer` · `dialog` · `alert_dialog` · `menu` · `select` · `combobox` · `toast` ·
`loading_overlay`.

**Skip entirely:** `popover` · `tooltip` · `preview_card` (all three are `:anchored`; all three are
inert on fresh Android). Skipping `popover` is only possible if you also skip `menu`'s auto-generated
sibling — `menu`'s catalog declares `necessary: ["popover"]` (`priv/mob/menu.exs`) and
`generate_necessary/1` **does not ask** (`lib/mix/tasks/mishka.ui.gen.mob.ex:266-278`), so
`popover.ex` and `anchored.ex` will land in
`lib/kati/components/` regardless. **That is fine — they are dead code as long as nothing calls
`popover/2` with a trigger.** Add a lint/grep in CI: `grep -rn "Anchored\.\(anchor\|closed\)" lib/` must
return nothing.

**Skip (not in the Kati design):** `tree_select` · `menubar` · `navigation_menu` · `floating_window` ·
`autocomplete` (unless the 19-search screen wants it) · `context_menu` (unless you also port
`combinedClickable`).

### 5.5 The one thing to verify on hardware first

Before building any of the 5 modal screens: `mix mob.new` a throwaway app, generate `drawer`, put a
`side: :bottom` sheet in the screen root, and confirm on a real Android device that
(1) the sheet draws over the page, (2) the backdrop dismisses, (3) the drag handle's `:canvas` reports
drags. Steps 1–2 are pure `:box` stacking and near-certain. Step 3 is the only one that depends on canvas
touch-coordinate scaling, which `mob-framework.md:1545-1548` records as a known cross-version drift point.
